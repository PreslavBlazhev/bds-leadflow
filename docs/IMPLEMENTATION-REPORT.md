## A. Резултат

Построено е пълно локално приложение с реален backend и постоянна SQLite база:

- 9 екрана: Днес, Нови клиенти/база, Обаждания, Pipeline, Последващи, Оферти, Клиенти, Статистика, Настройки. Плюс детайл на контакт, CSV импорт, преглед на оферта за печат и „Още“ за телефон.
- Домейн услуги за identity/дедупликация, eligibility, scoring, квоти, idempotent дневни списъци, 9-те резултата, DNC, follow-ups, оферти, клиенти/плащания, статистика, импорт/експорт, backup.
- Отделен worker: scheduler (prepare 07:00 / publish 08:00 Europe/Sofia) и outbox за push/имейл с fallback логика.
- Owner auth (Argon2id + DB сесии), CSRF/origin защита, SSRF-safe модул за проверка на сайтове, PWA (manifest, временна BDS иконка, service worker).
- 400 синтетични „ДЕМО“ бизнеса + fixtures + 3 дни история.

**Stack (фиксиран lockfile):** Next.js 16.4.0 (App Router, Turbopack), React 19.3, TypeScript 6.0.3 strict, Tailwind 4.3.3, Prisma 6.19.3 + SQLite (WAL), Zod 4.6.5, libphonenumber-js, tldts (PSL), @node-rs/argon2, web-push, nodemailer, papaparse, Vitest 3.2.7, Playwright 1.63 (системен Chrome).

| Резултат | Реален side effect | Тест |
| --- | --- | --- |
| Не отговори | CALL без разговор; етапът не се променя; по избор retry follow-up | T15 |
| Говорихме | CALL с разговор; „Контактуван“ само ако етапът е „Нов“ | T15, unit матрица |
| Да се обадя отново | изисква дата/час и отговор „имаше ли разговор“; CALL_BACK follow-up | T15, T16 |

| Спечелен клиент | изисква услуга/сума/дата; idempotent Client; приема избрана оферта; **без** получени пари | T15, T21, T22 |
| Отказ | „Загубен“ с причина; отменя отворените follow-ups | T15 |

**Fallback:** след публикуване → един push запис, разпратен към всички активни устройства. Без устройства или при окончателен отказ на всички → един имейл веднага. Иначе, ако до 30 мин. след по-късното от планираното и реалното публикуване списъкът не е отворен → един имейл (fallback по **липса на отваряне**, не доказателство за неуспешен push). Отварянето на „Днес“ го отменя; проверява се точно преди изпращане. `provider_accepted` ≠ доставено ≠ прочетено. Тестове T29–T34 (с mock транспорти).

## I. Сигурност и данни (известни рискове)

- Без „100% compliant“ твърдения. Правното основание за обработка на B2B контакти и правилата за директен маркетинг **не са проверени** (задача за go-live).
- DNC и минималните идентификатори се пазят за потискане. Пълното заличаване би отслабило дедупликацията (документиран компромис).
- Restricted Google съдържание не се записва (T41), но адаптерът не е проверен live.
- `npm audit` (Node 24, 08.10.2026): 13 общо (2 critical, 9 high, 2 moderate). Production веригата: 3 high — deepmerge-ts през prisma/@prisma/config. Prisma 7 **не** го поправя (уязвим диапазон 6.13 – 8.1.0-dev); npm предлага downgrade до 6.12.0. Останалите са dev/test tooling (vitest/tinypool/vite/esbuild/braces); поправката на vitest е 5.0.3 (Node `^22.12 || ^24 || >=26`). Не са правени major промени — приет риск за локалното демо, задача за go-live.
- `owner:create`: смяната на паролата (хеш + обезсилване на всички сесии + audit) вече е **атомарна** (преди беше на три стъпки). Не иска старата парола — достъпът до терминала се приема за собственост.
- SMTP няма idempotency → възможен дубликат при timeout след приемане.
- Backups в real ще съдържат служебни лични данни → нужно е криптирано съхранение.

## M. Ограничения и следващи 5 стъпки към live

Ограничения: само локално; кандидатите са синтетични; известията не са доставяни реално; SQLite е за един сървър; глобалният Node 21.5 е извън поддържаните engines (проектът е проверен на Node 24.21.0); един E2E провал от първата сесия остава неизяснен.

1. **Източник на кандидати:** избор на B2B доставчик или Places (CRM употреба) + правен преглед → адаптер, field policy, budget cap → e2e тест.
2. **Импорт на старата история** от Excel→CSV и преглед на „За проверка“, преди първия real списък.
3. **Hosting:** always-on сървър с HTTPS, `APP_MODE=real` на `data/real.db`, два процеса под process manager, ежедневен backup извън сървъра.
4. **Известия:** production VAPID → абониране на телефона през HTTPS → реален тестов push. SMTP доставчик + owner адрес → реален тестов имейл.
5. **Среда:** глобален Node 24 LTS → `npm ci` → `npm run check` + `npm run test:e2e`. Отделно решение за `npm audit` (deepmerge-ts в Prisma веригата; vitest 5 изисква Node ≥22.12) — без major промени само заради номера.
