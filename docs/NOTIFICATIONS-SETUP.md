# Известия: Web Push и резервен имейл

Статус (09.10.2026): кодът е готов и проверен с mock транспорти, с истинските адаптери в dry-run (без мрежа) и в production профил локално. **Нито едно известие не е изпратено реално; телефонът не е тестван.** Web Push изисква HTTPS адрес — localhost абонаментите не важат там.

## Път на известието

1. Worker-ът публикува дневния списък → **в същата транзакция** се създават два outbox записа: `push:daily:<дата>` и `email:fallback:<дата>` (уникални ключове). Известие „списъкът е готов“ се създава само при действително публикуване. Блокиран нов списък (активен неприключен, уикенд, преди 08:00, без кандидати) → няма известие. Отделно напомняне за останалите контакти не е добавено (няма втори ежедневен шум).
2. Outbox: claim с условен UPDATE + lease (2 мин) → два worker-а не изпращат един запис; без отворена DB транзакция по време на HTTP/SMTP. Пазят се `attempts`, `notBefore` (due), `status`, `providerMessageId`, `lastError`, и всеки опит в `DeliveryAttempt` (резултат, HTTP код). Retry с експоненциален backoff, максимум 5 опита.
3. Статуси: `provider_accepted` (прието от push доставчика/SMTP сървъра) ≠ показано ≠ прочетено. `simulated` = demo или `NOTIFY_DRY_RUN`. `skipped` = остаряло/ненужно. `acknowledged` = owner е отворил списъка. `cutover_hold` = пренесено, чака ръчно решение.
4. Дневно известие за **минала** местна дата никога не се изпраща (`skipped`).

## Web Push

- Стандартен Web Push + VAPID (`web-push`), service worker `public/sw.js` (scope `/`, относителни адреси → работи на canonical HTTPS origin-а), manifest `start_url: /today`.
- Payload: само заглавие, текст с бройки, `url: /today` и еднократен `rt` token. Без имена/телефони на потенциални клиенти (тест).
- Телефон: Настройки → „Известия и устройства“ → **„Активирай известията“** (разрешението се иска само след натискане). Показва: неподдържан браузър, не-HTTPS, отказано разрешение (как да се промени), „абонамент в браузъра, но не е активен за този адрес/база“ (напр. след смяна на адреса), iPhone: нужно е „Добави към началния екран“ (iOS/iPadOS 16.4+). „Изключи на това устройство“ = unsubscribe + revoke в сървъра.
- Сменен VAPID ключ → старият абонамент се заменя при „Активирай“. `pushsubscriptionchange` в service worker-а прави нов абонамент и го регистрира (ако сесията е валидна).
- 404/410 от доставчика → абонаментът е `expired` и не се ползва повече; другите грешки → retry.
- Разписки (не доказват прочитане): след `showNotification` service worker-ът изпраща `shown`, при натискане — `clicked` (`POST /api/push/receipt` с token-а; в базата е само sha256; Origin проверка). Записва се `swReceivedAt` („обработено от service worker“) и `openedAt` („отворено от owner“). Без мрежа на телефона разписката не пристига — тогава резервният имейл може да дойде, въпреки че push-ът е показан.
- Service worker-ът кешира само `offline.html`, иконите и manifest-а. Всички `/api/*` и CRM страници минават през мрежата, без кеш; offline навигация показва само статичния offline екран.

## Резервен имейл — точна дефиниция

Един SMTP адаптер (nodemailer), един получател `OWNER_NOTIFY_EMAIL`, подател `SMTP_FROM`. Интервал: Настройки → „след N минути“ (по подразбиране 30).

Изпраща се (един на ден, ключ `email:fallback:<дата>`):
- **веднага**, ако push не може да бъде опитан или е окончателно отказан: няма активни устройства, push не е конфигуриран, всички устройства отказват (вкл. 404/410), изчерпани опити;
- иначе в **max(планиран час, действително публикуване) + N минути** — изчислено от действителното публикуване, т.е. при закъснял старт (напр. 09:12) имейлът е в 09:42, не в 08:30;

освен ако непосредствено преди изпращането: owner е отворил днешния списък (екранът „Днес“ записва `DailyAcknowledgement` → `acknowledged`), или service worker на устройство е потвърдил показване (`swReceivedAt` → `skipped`).

`provider_accepted` от push доставчика **не** спира имейла. Отварянето на сайта не се третира като доказателство, че push е получен — то означава само, че owner вече е видял списъка, затова имейлът е излишен.

## Дубликати и ограничения

- DB: уникален `dedupeKey`, claim/lease, `DeliveryAttempt` по устройство (повторният опит пропуска вече приетите устройства).
- Неизбежен прозорец: доставчикът е приел, процесът пада преди записа → при следващия опит може да има повторение. Web Push няма idempotency ключ; SMTP получава детерминиран `Message-ID` (`<email.fallback.<дата>@bds-leadflow.local>`), което помага на някои клиенти да скрият дубликата, но не е гаранция. Exactly-once външна доставка не се обещава.

## Конфигурация (worker, освен публичния ключ)

`NEXT_PUBLIC_VAPID_PUBLIC_KEY` (група — същият в web и worker), `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` (`mailto:`), `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`, `OWNER_NOTIFY_EMAIL`. Gates: `DELIVERIES_ENABLED`, `NOTIFY_DRY_RUN`, `ALLOW_REAL_TEST_DELIVERY` (web). Ключове: `npx web-push generate-vapid-keys` локално; смяна на ключа изисква ново „Активирай“ на всички устройства.

## Какво е проверено / какво остава

| Проверка | Статус |
| --- | --- |
| Mock push/имейл: успех, временна грешка, 404/410, всички отказани, без устройства → имейл веднага, закъсняло публикуване → по-късен имейл, отворен списък отменя имейла, без дубликати при паралелни worker-и | реално проверено локално (SQLite и PostgreSQL) |
| Разписка „shown“ спира имейла; `provider_accepted` сам не го спира; минала дата → skipped; `cutover_hold` не се обработва | реално проверено локално |
| Истинският web-push адаптер (VAPID подпис + криптиране) и SMTP адаптерът в `NOTIFY_DRY_RUN` — без мрежа, статус simulated | реално проверено локално |
| Production профил: worker публикува, push „няма устройства“ → имейл веднага → изграден в dry-run | реално проверено локално |
| Доставка до телефон, показване, разписка от реален service worker, iPhone PWA | **не е проверено** (нужни са HTTPS адрес и телефон) |
| Реален SMTP / попадане в Inbox (SPF/DKIM) | **не е проверено** (няма credentials) |
